# Handoff — C-21290 looped `group` opened as columns

**Date:** 2026-10-01 (updated 2026-10-02)
**Ticket:** C-21290 (SUP-781, ClearCompany) — CDS turns looped `group` elements into columns without the loop
**Branch:** `geraldosilva/c-21290-clearcompany-cds-turns-looped-group-elements-into-columns`
**Status:** fixed, verified in Studio against real sends. Frontend PR vendors this build.

## Cause

`convertElementalToTiptap` mapped every `group` to a column layout (a leftover from designer 0.3–0.7, which saved column blocks as `group`) and never read `loop`. Opening the template rewrote it as `columns`, so the loop was lost on the next save. The renderer has never drawn `group` as columns: it flattens the children into the parent and repeats them per `loop` item.

## What changed

- New `group` tiptap node (`content: "block*"`) holding `loop`, `if`, `locales` and every other field as `elementalProps`; both converters round-trip it. Every `group` now opens as a group, including the old designer-saved column shape (it was always sent stacked).
- Canvas: children line up with top-level blocks (no 40px strip, handles in the gutter). Editor-only chrome: dashed frame, a loop tag (`LoopBadge`, shared with looped lists), side hit strips that outline/select the group. Hidden in the rendered preview, shown with "show variables".
- `GroupForm`: loop on/off, data path, conditions. Group block in the sidebar (starts with one paragraph; duplicates get fresh child ids).
- Preview: `renderElementalPreview` repeats a looped group per item with `$.item`/`$.index`; an empty array renders nothing, as the send does.
- `$.item` chips are valid inside a looped group (`chipScope`). A bare loop path (`data.products`) is reported as a variable; `extractLoopShapes` (exported, and `useVariables().loops`) reports each loop's item fields so hosts can collect array data.
- Typing in a lone group's block no longer hands the selection to the group: `Email.tsx`'s "select the only block" effect runs after every save, and now skips while the editor has focus.
- DnD: a group's top/bottom 12px strips drop before/after it, its body drops between its children (empty groups too); a block cannot be dropped inside itself and a same-position move is a no-op. Edges are measured on the content box, so the placeholder opening up no longer flips the target. Dropping on the grey canvas below the email appends after the last block, with one indicator; the card's and canvas's drop zones share that indicator, since drawing it grows the card under the pointer and each zone used to clear the other's (blinking). A drag-end monitor clears stale indicators.

## Evidence

- vitest 4643/4643; `group.roundtrip.test.ts` fails 5/6 with the converter and preview changes reverted.
- Playwright `e2e/group-drag-and-drop.spec.ts` (11 cases): fails 6/9 with the DnD fixes reverted; the end-indicator case reproduces the blink (indicator 0,0,1,1,…) with its fix reverted. `e2e/group-typing.spec.ts` selects the group instead of the typed-in block with its fix reverted. 97 DnD/group/selection e2e pass. `editor-dev` serves `dist`, so `pnpm run build-code` before running it.
- Dev sends (`/messages/{id}/output`): SUP payload, designer-saved drafts and a list+group template render the same blocks and order as the canvas preview; empty arrays render nothing.
- Final pass 2026-10-02: an API-created template (looped group + looped list + plain group) and a designer-built one (text, looped group holding a list and text, text, looped list) both save the expected Elemental and Studio's preview matches the dev render.
