# Session Handoff: C-20405 — Inbox localization drops the body

**Date:** 2026-09-02
**Session Focus:** Traced why a localized inbox preview renders a blank body, found a second (silent) data-loss defect in the same code path, and fixed both.
**Branch:** `seth/c-20405-studio-inbox-localization-preview-renders-blank-body-and`, based on `origin/main` at `dd9b4f39`.
**Companion PR:** `trycourier/frontend` — same branch name, fixes the writer that produces the mismatched shape.

## Origin

Reported against template `nt_01m1he8v4pect919jrz73g2qz2` (workspace `afbeeb4b-2021-4380-9dd5-eb4cc37106c0`, staging): selecting a translated test event in Preview & Test shows the localized **title** ("Hello" → "Hola") but the body disappears entirely — it does not even fall back to the source language.

Investigation started from trycourier/backend#10141 (C-20378, push title localization), on the theory that inbox had the same bug. It does have that bug, but it is not this one — see "Not fixed here".

## Root cause (verified, not inferred)

Inbox is the only channel whose designer **rebuilds** its content nodes into a fixed
header/body/actions shape on load, from a field whitelist, rather than transforming them.
Push's content memo maps `meta` → h2 and returns every other node by reference. The
inbox rebuild is load-bearing — `createTitleUpdate` reads the editor's output
**positionally** (`textElements[0]` = title, `[1]` = body), so the rebuild is what
guarantees header-first ordering and a header node even when no `meta` exists — but it
was written to reconstruct nodes rather than transform them, so it dropped every field it
did not name.

The body is stored in the plain form with its translation in the rich form:

```jsonc
{ "type": "text", "content": "How are you?",
  "locales": { "es-mx": { "elements": [{ "type": "string", "content": "¿Como Esta?" }] } } }
```

`applyLocaleToContent` promotes the node to `elements` and deletes `content` (deliberately,
so `convertElementalToTiptap` picks up the translation). `getOrCreateInboxElement` then read
`.content`, found nothing, and emitted `"\n"`.

**Defect 1 — blank localized preview.** Verified against the real functions and the exact stored payload:

```
locale=(none)   -> header: "Hello\n"   body: "How are you?"
locale=es-mx    -> header: "Hola\n"    body: "\n"        <- matches the report
```

The title survives only because it is passed through as a scalar (`metaElement.title`).

**Defect 2 — editing destroys body translations.** The load-side rebuild strips `locales`
before the editor sees the node, and `createTitleUpdate` rebuilds the body as
`{ type: "text", content }` with no `locales`. Verified load → edit → save round-trip through
the real `getOrCreateInboxElement` / `convertElementalToTiptap` / `convertTiptapToElemental` /
`createTitleUpdate` / `updateElemental`:

```
inbox edit=none  | title xlat: kept | body xlat: LOST
inbox edit=title | title xlat: kept | body xlat: LOST
inbox edit=body  | title xlat: kept | body xlat: LOST
push  edit=none  | title xlat: kept | body xlat: kept
push  edit=title | title xlat: kept | body xlat: kept
push  edit=body  | title xlat: kept | body xlat: kept
```

Lost even on a **title-only** edit. The meta title survives via `getExistingMetaElement`;
action nodes survive via `cleanInboxElements`. The body was the only node with no carry-forward.

## Ruled out (a hypothesis that did not survive)

An earlier reading of this session claimed the loss fires merely on *opening* the template,
because `InboxEditorContent`'s restoration effect calls `editor.commands.setContent(newContent)`
with no `emitUpdate: false`. **That is wrong.** `setContent` defaults to `emitUpdate = false`
in `@tiptap/core` 2.12.0 (`dist/index.js:2472`), so the restoration effect does not fire
`onUpdateHandler`. A real editor interaction is required. Recorded here so nobody re-derives it.

## Decisions made

- **Kept the normalizer; did not switch inbox to a push-style passthrough.** BECAUSE
  `createTitleUpdate` reads the editor output positionally, so a passthrough would (a) emit no
  header row when `meta` is absent, making the next keystroke promote the body to title, (b) be
  sensitive to storage order, and (c) display extra text nodes that the save path deletes on first
  edit. Push has no positional contract, which is why passthrough is safe there. STATUS: confirmed.
- **Imported `extractPlainTextFromNode` from its module, not the `@/lib/utils` barrel.**
  BECAUSE several suites replace that barrel wholesale with `vi.mock`. Fixing the mock with
  `importActual` was tried first and cascaded into the same file's jotai mock. STATUS: confirmed —
  full suite green with the direct import and no test-file changes.
- **Preserved only `locales`, not the whole node, on the rebuilt body.** BECAUSE styling fields
  do not round-trip through the inbox save path anyway, so spreading them would show the user
  formatting the editor silently discards. STATUS: confirmed, narrower blast radius.

## Not fixed here (tracked on C-20405)

- **Backend inbox title precedence.** `get-template-config.ts::resolveInboxConfig` still lets an
  explicit `channels.inbox.title` beat the locale-resolved content title — the inbox half of
  C-20378, deliberately deferred in that PR.
- **Duplicate inbox title rows.** `createTitleUpdate` writes both `meta.title` and
  `raw.title` for inbox (push writes only `meta.title`), so `extractTextFields` yields
  `inbox.0.title` and `inbox.raw.title` with independent `locales` maps. Not triggered by the
  reported template, which has no inbox `raw`. Note upstream `dd9b4f39` now reads `raw.title`
  in `getOrCreateInboxElement`, which changes the shape of this problem — re-check before filing.
