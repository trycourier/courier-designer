# Handoff — C-21259 SMS/Push editors open blank on markdown bold

**Date:** 2026-10-07
**Ticket:** C-21259 — SMS and Push editors (and their Preview & Test) render nothing when a text block contains `**bold**`
**Branch:** `geraldosilva/c-21259-sms-push-bold-blank` (off `origin/main` at `6c27b8de`)
**Status:** fixed, verified in Studio on localhost:3000 against the dev API. Frontend PR vendors this build after merge.

## Cause

SMS and Push build their editor with `textMarks: "plain-text"`, so the schema has no bold/italic/strike/underline marks. `convertElementalToTiptap` still turned `**x**`, `_x_`, `~x~`, `+x+` into those marks; ProseMirror threw `There is no mark type bold in this schema` and Tiptap fell back to an empty doc with only a console warning.

## What changed

- `convertElementalToTiptap`: for `sms` and `push` channels, the markdown emphasis patterns are skipped, so the markers stay literal text. Variables, handlebars and links still parse. Same module-flag pattern as `withLiteralText`.
- The reverse converter writes the literal markers back unchanged, so a save keeps the stored text.

## Evidence

- vitest 4629 passed; `plainTextChannelMarks.test.ts` (4 tests) fails 3/4 with the converter change reverted.
- Studio, probe template `nt_01m3m3z3pdfak9qb0pjswz4trc`: SMS editor shows both blocks (counter 23), Push shows `P1 **{{data.s.name}}** tail` with the variable chip, Preview & Test shows both channels. Draft SMS/Push content unchanged after opening.

## Open / deferred

- In-App (Inbox) also uses `plain-text` and likely blanks the same way on markdown.
- SMS/Push content stored in the elements-array form with `bold: true` flags still emits a mark and would blank the editor.
